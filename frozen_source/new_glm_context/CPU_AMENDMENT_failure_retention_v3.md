# Append-only v3 correction: persist every engine return before validation

The v2 CPU freeze was SHA256 8bc1b739ace0120922450920be559351ee3b23dcdeb0899885edd7cb0588833d. No real new model judgment or root GPU authorization existed when the independent reviewer exercised the actual runner with a fake engine. The reviewer found a real failure: a returned-count mismatch raised before any returned raw strings were saved; a middle response's prompt-token mismatch could preserve only earlier canonical rows and lose later returned raw strings. The v2 code and manifest, its independent failing fixtures and all attempted repairs are retained. v2 did not provide the promised failure-retention property and is explicitly superseded.

The new generation_receipts.py module is independent of any model, task labels or GPU library and may be copied into the separate SNLI runner. The same blocking generate path is used for scientific and diagnostic calls. Before invoking the engine it durably appends the expected batch IDs, mode, diagnostic flag and expected input/grammar hashes. Actual engine request IDs and complete prompt IDs are recorded at ordered input processing as provisional bindings. After generate returns, every returned request and every completion is snapshotted into one append-only receipt containing engine ID, observed position, every untrimmed raw completion, all output token IDs, complete actual prompt token IDs and hash, finish/stop information, expected batch IDs and explicitly unverified positional candidates. That full receipt is flushed and fsynced before count, order, engine-ID, prompt, grammar, completion-count or label-parse checks.

A separate append-only validation event records each verified or failed binding. Canonical scientific/diagnostic rows can be emitted only after successful batch validation and link back to the generation call, raw-return position and receipt SHA256. Unknown, duplicated, additional or out-of-order returns are not assigned to a trusted scientific request by position. If a later parser/collector exception occurs, all earlier and later actual returns remain in the already persisted whole-batch receipt. There is no automatic retry. If generate itself raises without returning a sequence, a durable failure event retains expected/processed IDs and marks actual return count and completion cost unknown; it does not invent a zero cost or an empty successful response.

RAW_RETURN_ACCOUNTING.json and the reanalysis cost authority read the raw invocation/return/validation ledgers, including invalid or unmapped payloads, rather than counting only canonical parsed rows. Observed token payload totals are kept separate from fully attributed compute totals. Missing, malformed, unknown or failed invocations leave complete token totals as null, not zero. Repeated references to the same raw receipt or duplicated engine IDs do not create additional scientific observations; distinct fresh calls may return identical payloads. Canonical reanalysis also checks engine-ID uniqueness and the complete chain from canonical call ID/position/raw/hash/tokens to the raw receipt, successful binding and engine-processed call ID. This prevents reuse of one response across identical repeat prompts.

CPU regression executes the actual runner source with a fake vLLM engine, without importing a real GPU runtime. It covers missing/extra scientific and diagnostic returns, a middle prompt-token mismatch, reordered returns, unknown/repeated engine IDs, multiple completions, invalid untrimmed JSON, a middle collector exception, an engine exception, empty/None returns, and successful execution. Separate mutations verify rejection of canonical duplicate engine IDs under identical prompts/grammars, wrong raw-return positions, changed raw labels and wrong call IDs. The independent reviewer reruns the real failure cases before v3 is frozen. These are synthetic CPU records, never model judgments.

No source weight, selected target/background ID, complete field, prompt byte/token, grammar, sampling setting, scientific schedule, model-call budget, point-estimate function or original analyze.py/secondary.py byte is changed by this retention correction. Its added durable I/O is part of the newly recorded runtime, and no online latency claim is made. The root's separately supplied, pre-inference GLOBAL_PRIMARY_AMENDMENT defines the nine-comparison current suite primary criterion; the old 98.75% flags remain legacy outputs rather than the new global primary decision.

The new freeze must include the original v2 bytes, complete code diff, before/after hashes, evidence that all prepared inputs and source/model identities remain unchanged, this amendment and the independent negative-test result. Only that final new SHA may be authorized for GPU execution.
