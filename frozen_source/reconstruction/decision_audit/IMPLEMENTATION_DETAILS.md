# Decision audit implementation details — before new development judgments

The root task approved the independent design for implementation, not GPU inference. Development and evaluation are separate launches and permission/verification stages. The old context audit and its198-file handoff manifest remain untouched.

Task order is DBLP–ACM then BoolQ. Each task uses reserve ordinals0..127 as exposed development and128..255 as held-out evaluation. Numeric occurrence IDs are1..128 within each task/split relation, while ledgers always retain task, split, original source ID and reserve ordinal. Whole original fields are preserved. No fillers, target-only output scope, label balancing or new target exclusion is introduced. Complete relations and all plan partitions are frozen before new development outputs.

Grouping seed is2026110207. For each task/split, random grouping uses a Python Random stream seeded by the integer SHA-256 of the compact JSON tuple `[2026110207,"random",task,phase]`. A single shuffle is reused as the base permutation for k2/4/8 consecutive chunks. Diversity grouping starts each new batch at the remaining occurrence with the smallest SHA-256 string of `[2026110207,"diversity-anchor",task,phase,occurrence_id]`. It then greedily picks the remaining occurrence minimizing its maximum cosine similarity to the current batch, ties by numeric occurrence ID. It never uses labels or model predictions. Partitions are separately built for each k and cover each relation exactly once.

Lexical features use the same word unigram/bigram representation as the completed context audit: lowercase Unicode word regex `(?u)\b\w+\b`, raw term counts, smoothed IDF `log((1+N)/(1+df))+1`, L2 normalization. Fit only on the already-frozen task training background bank; transform both relations without refitting. This is a declared greedy diversity adaptation, not a faithful reimplementation of the complete BATCHER demonstration-selection system.

Development schedule seed2026110208 and held-out schedule seed2026110209 each shuffle the full task/configuration/repeat/batch request list once. Singleton calls are included in the same schedule. Both models share schedules and block membership, up to64 requests per blocking generate invocation with maximum16 engine sequences. Main model/runtime settings remain the previously verified settings. Each phase/model must pass its own recorded controls before scientific requests; diagnostic calls are distinct from the14592 planned scientific calls.

Fresh singleton references use the same stable numeric IDs and source feature strings as each relation's batches. The old context audit's local-ID-1 singletons are never reused. Singleton reference assignment is S1,S2 for two-observation candidates and S1,S2,S1,S2 for the canonical four-observation control. A singleton policy's test fidelity uses off-diagonal S1 versus S2, while gold and COUNT use its actual execution S1 or S2.

Selection compares integer errors exactly: tolerance .05 is `20 * errors <= 128 * observations`. Incomplete references or candidate executions never reduce the denominator. Choose eligible largest k, then lowest exact disagreement fraction, then random before diversity, then canonical before the alternative order; no eligible batch falls back to singleton. Gold cannot enter the selector. All policies and eligibility ledgers are hashed after both development runs and must receive independent/root approval before the evaluation runner can load scientific evaluation requests.

The primary evaluation is the exact fixed-holdout census of Output minus Input fidelity/calls in each of four settings, with each replay, empirical tolerance indicator and observed-dominance rule preserved. No IID binomial test, Clopper–Pearson certificate, population superiority claim or nominal confidence interval is computed. Actual batch membership creates within-prompt dependence. COUNT sums all128 actual relation members before comparing with gold and abstains on an incomplete condition. Full-grid evaluation does not select or alter a policy.

Costs are separately attributed to scientific research execution, the1152-call standalone development budget of each selector, each selected deployment plan, and diagnostics. Equal requested-label/call budgets do not force equal observed tokens or runtime. One128-row query cannot amortize1152 calibration calls against128 singleton calls. Call break-even, when displayed, is arithmetic under reuse; equal-cost thresholds for k2/k4/k8 are18/12/11 relations, while strict saving first occurs at19/13/11. No new relation beyond the one held-out relation per task has yet validated that extrapolation.
