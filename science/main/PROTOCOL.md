# Frozen pilot protocol (written before inference)

Purpose: compare three Qwen3-4B-Instruct-2507 execution plans on a reconstructed, biased candidate-pool task. This is a pilot, not a claim of deployment readiness.

Data: test.jsonl.zst from nixiesearch/amazon-esci commit c092c898ccc036577f25a998fd429b84facfbd86, SHA-256 ede7f2ed1e45a1563bdea8d8e96184c4dd5eb585af0856b2268bc82e37124087. The publisher's convert.py groups by original query_id and emits one row per E product, with all S/C/I products and scores 0.1/0.01/0.0. IDs and other E products are omitted. Grouping by exact query string in this pilot can conflate distinct query IDs. Retain the first eligible row for each exact query string, then apply reservoir sampling without replacement, seed 20271030, to choose 160 strings. Eligibility: non-empty query/doc, aligned non-empty neg/negscore, known score codes and nonempty negative texts. For each sampled row, take at most seven negatives using a query-specific deterministic seed and shuffle with its single E product. Each constructed pool therefore has 1 E product and up to 7 non-E products; pools are not the full original retrieved lists or representative of population prevalence. Product text is limited to the first 600 characters; this can remove evidence available to the original annotator.

Target: map original E and S to positive, and C and I to negative, as an operational proxy for satisfaction. An S grade indicates a substitute, not necessarily an accepted purchase. Compare predicted labels against these inherited ESCI judgments, not new human annotations. Report candidate precision, recall, F1, accuracy, and mean absolute per-pool ratio error only conditional on complete, validated pools; always report pool completion and attempted denominator separately. Report class distribution, errors for each source grade, wall time and token counts. Do not claim population prevalence or causality. Compare the same pool and candidate order for all plans. No adaptive changes to prompts or selection based on held-out results.

Plans: (1) direct pointwise Y/N, one independent prompt per candidate; (2) direct batched JSON, one prompt per pool; (3) two-stage query-only JSON specification plus batched JSON labels. Temperature=0; generation caps are 4, 192, and 160+192 output tokens respectively. A batch is valid only for a JSON array of exactly n distinct indices 1..n and strict Y/N strings. A malformed batch receives at most one fresh full-batch retry; failed pools are excluded from quality metrics and counted as failures, not filled with negative labels. A malformed specification receives at most one fresh retry; failures do not reach stage 2. Pointwise has at most one retry per malformed answer. Time is measured for offline batched generate calls, excluding model load and Python bookkeeping; token counts include retries. These settings measure aggregate offline throughput on one GPU and do not estimate online tail latency.

Keep raw model outputs, selected input rows, scores, prompt code, model and runtime information, and detailed results. One run on the test split; report execution bugs or environmental retries transparently. No parameter tuning against this test run.

**Timing clarification:** The recorded interval includes chat-template rendering as well as the batched generation call; it excludes model loading and most other Python-side prompt assembly and parsing.
