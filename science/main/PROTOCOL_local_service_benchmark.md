# Post-hoc local HTTP service benchmark

This benchmark is fixed after observing all existing WANDS results and before running the measured conditions. It reuses the same 52 WANDS query pools and 1,664 judged candidates; it is not a new test dataset or a production deployment. Its purpose is to measure complete local request pipelines rather than infer speed from logical call counts. The human relevance labels, source-text truncation, possible model pretraining exposure, repeated products, and sampling limitations remain unchanged.

## Service and execution

Run a single Qwen3-4B-Instruct-2507 instance with recorded model hashes in vLLM 0.10.2 V1, bfloat16, eager execution, 4,096-token context, a maximum of 16 active sequences and GPU memory fraction 0.70 on one RTX 5090. Serve HTTP only on `127.0.0.1`. Disable prefix caching to avoid cross-condition cache reuse. The local client uses one persistent HTTP connection pool, no remote service, and records actual request and query completion times; model loading, server startup, unrelated synthetic warmup and constraint controls are excluded. The client sends non-streaming requests at temperature zero using v0.10.2 `guided_regex`. No output API key or credential is needed. Retain server launch arguments, version and startup log without credentials.

Before any measured candidate query, require the incompatible BANANA negative control to confirm both the fixed-key JSON and Y/N regex constraints; warm all three plans with an unrelated synthetic query. Each measured query starts after acquiring a client concurrency slot and finishes once all of its required HTTP responses are parsed and the pool result is assembled. This duration includes the query specification request, client work, local HTTP transport, server queueing and generation; waiting for the client slot, model loading, initialization and final result-file writing are excluded. Thus it is local active-query latency, not internet latency or a production SLA. Each query makes at most one retry for a structurally invalid model response. A network or HTTP failure is not silently retried or imputed. A twice-invalid specification falls back to the direct prompt; a required candidate response that remains invalid or fails causes pool abstention.

All three plans use fresh specifications and the same task instruction and prompts as the 52-query selective experiment. Within a query, fan out available requests concurrently; server batching remains enabled. The plans are:

1. `pointwise`: issue all 32 guided Y/N requests after the specification.
2. `keyed`: issue four original-order, eight-item fixed-key guided JSON requests after the specification.
3. `selective`: issue original and stable-ID reversed keyed requests for all four chunks concurrently; if any required keyed output remains invalid, abstain. Issue pointwise requests only for valid disagreements, then combine the actual returned values with the agreeing keyed labels.

Each plan runs at active-query concurrency 1 and 4 over all 52 queries. Run two repeats of each of the six plan/concurrency combinations. Shuffle the first-round condition order using Python `random.Random(20271231)`; reverse it for the second round. Within each round use a fixed query shuffle from `random.Random(20271231 + repeat)` shared by every condition in that round. Fresh specifications and inference may differ across plans and repetitions, so comparisons do not isolate a pure scheduling treatment or reproduce the earlier offline predictions. Include specification failures, candidate failures, all initial/retry requests, prompt hashes, output text, per-request logical input/output tokens, per-pool predictions and active-query timestamps in the artifact.

## Analysis fixed before measurement

For every condition and repeat, report attempted/completed pools, pooled candidate F1 and balanced accuracy and query-macro ratio MAE on complete pools, active-query latency p50/p95 among complete pools, complete-pool throughput (completed pools divided by condition wall time), model calls and logical input/output tokens. Report incomplete pools separately so failure cannot be interpreted as lower latency. Also report each repeat rather than treating two repetitions on the same queries as independent samples. No p-value, significance threshold, general speedup, online cloud cost or cross-hardware claim is specified. Report adverse, null and failed outcomes. Concurrent pointwise requests can be batched by the server; counts alone cannot establish latency.

Fix hashes of this protocol, the client/analysis/verifier code, the saved 52-query selection and the original prompt/parser code before measured execution. Verify raw outputs, ID associations, retries, per-query timing, aggregate metrics and throughput independently. A local closed-loop workload on one GPU cannot represent Internet access, production traffic, tail guarantees or other hardware, and plan comparisons also change model calls and specifications.
