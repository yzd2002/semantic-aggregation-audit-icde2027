# Order-disagreement fallback: a new disjoint WANDS sample

This protocol is written after seeing the earlier compact and keyed WANDS results, but **before selecting this sample or running the new inference**. The earlier keyed audit uses already exposed pools, changes prompts and formats together, and does not prove a model-internal position effect. The present question is whether a pre-fixed, two-presentation disagreement fallback changes a *query-level ratio MAE* relative to the fixed-ID keyed original-order plan on a further unseen sample. The sample comes from the same public WANDS source, not a new data source or a purchase-satisfaction study; pretraining exposure is unknown.

## Selection fixed before inspecting this sample

Verify the three pinned WANDS source hashes, unique keys and foreign keys. Collapse repeated identical labels for a query–product pair to the smallest annotation ID; remove conflicting-grade pairs. Exclude normalized query strings (trim and case-fold) used in the pilot, validation and original ESCI samples, the first 160-query WANDS sample and the prior WANDS holdout. Exclude every product ID actually sampled in either previous WANDS sample. Retain only nonempty distinct normalized queries with at least 32 remaining nonconflicting judged products. The eligibility count was checked without inspecting grade rates before writing this protocol. Sort eligible IDs and uniformly sample 96 without replacement with `random.Random(20271126)`. For each query, sort eligible records by annotation ID and product ID, sample 32 and shuffle them using a query-specific RNG seeded by the first eight bytes of SHA-256 of `20271126`, a NUL, and the decimal query ID. Do not stratify on grade or replace cases after seeing outcomes. Preserve source identifiers, query, truncated product text, labels and final order; verify selection independently against pinned source tables. Products may recur across new queries, and exclusions concern *sampled* products, not all products ever present in source tables or model pretraining.

## Fixed model and plans

Use Qwen3-4B-Instruct-2507 with the recorded local model/tokenizer hashes, vLLM 0.10.2 V1, bfloat16, temperature zero, one RTX 5090, eager mode, 4,096-token context, prefix caching and 16 concurrent sequences. Use the existing WANDS exact-only system instruction, product serialization and specification prompt. Generate one query-only specification, with a 160-token cap and one retry; if invalid after retry, use the existing direct fallback with no specification for all plans of that query. Preserve specifications and failures.

Split the 32 candidates into consecutive chunks of eight, retaining the assigned local IDs. Use the prior keyed JSON prompt and fixed-key regex on (1) the original list, (2) an identical-prompt replay, and (3) a reversal inside each original chunk with each ID still attached to its product. The JSON keys are constrained in ascending numeric order; parse by ID. Use a 128-token cap and one retry after invalid output. Independently execute a pointwise prompt consisting of the same query, the same specification if valid, and one product text, requesting exactly one Y or N; constrain output to `[YN]`, use a four-token cap and one retry. Run pointwise for all 3,072 candidates so that it is a full baseline; then replay identical pointwise prompts once only for the items where the two keyed outputs disagree and pointwise output is available. Preserve all raw outputs, first/retry results, finish reasons, prompt hashes, ID mappings and completion flags. Before candidate evaluation, verify the JSON and Y/N constraints using an incompatible BANANA instruction both with and without each regex; abort on failure. Check the longest actual or retry prompt plus output cap against the context limit.

For each product, the **fixed agreement-fallback plan** uses the keyed label if original and reversed labels agree; on disagreement it uses that product's pointwise label. An invalid keyed chunk or unresolved needed pointwise response makes the corresponding pool non-estimable; never replace a missing label with N or silently drop it. The complementary secondary plan resolves the same disagreements using the pre-existing all-query-words lexical baseline. A simpler canonical-ID presentation is a necessary comparator: the sampled original chunks have IDs in ascending order, so their original keyed outputs are the canonical keyed plan. Sorting the same members by stable IDs removes dependence on their presented order at the prompt level; it does not protect against changed chunk membership, unstable IDs, numerical reruns, semantic errors, or determine which original ordering is best.

For a fixed pair of cached keyed outputs `a` and `b` mapped to the same IDs and one fixed pointwise result `h` per disagreeing product, `g(a,b,h)` is symmetric under swapping `a` and `b`: agreeing labels are unchanged and disagreements use the same `h`. This is a structural property of the cached combination, not a guarantee that recomputing nondeterministic model outputs or changing chunk membership preserves the answer. Equality does not prove correctness. Include exhaustive finite-vector tests.

## Analysis fixed before inference

Primary comparison: on pools completed by the original keyed, keyed replay, reversed keyed and all-candidate pointwise plans, compute the **query-macro ratio-MAE difference** (agreement-fallback minus canonical keyed original) against Exact=Y, Partial/Irrelevant=N. Use 4,000 paired query-cluster bootstrap resamples, NumPy `default_rng(20271127)`, and the 2.5th and 97.5th percentiles. Report the result regardless of direction and whether its upper endpoint is below zero; this is a sample-specific criterion, not a guarantee for other queries, other product populations or real user satisfaction. The source label mapping is a relevance proxy and annotators had access to information the model may not see.

Secondary results: pooled candidate F1, balanced accuracy, ratio MAE, completion over all attempted pools, keyed and pointwise replay changes, the proportion of items requiring fallback, and comparison against the all-candidate pointwise and deterministic all-query-words baselines, plus the lexical-fallback plan. Report paired intervals for F1 and ratio MAE as descriptive, without multiple-testing claims. The single-model, one-GPU, same-source evaluation is selected after earlier experiments, can contain product recurrence across queries and is affected by prompt, execution order, caching and missing information. No architecture-level, general speedup, online-latency or causal mechanism claim is warranted.

Report realized logical requests and tokens from each run. The number of calls for the fallback plan is a trace-derived *virtual count*: one specification plus applicable retries, two keyed batches per chunk plus applicable retries, and a pointwise call plus applicable retry only for disagreeing products. The actual baseline was run on all candidates, and diagnostics add replay calls, so do not present this count as measured online time or a proportional acceleration. Retain all runs even if the plan worsens quality.
